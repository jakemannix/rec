# Local M4 Max build

The local source now selects the tested 64/64/64 profile for the 40-core M4 Max through normal device detection. The CLI allows the chip family, and the engine verifies the GPU core count before loading the model. The 32-core variant and unknown core counts fail explicitly. No experimental shader transformations are enabled.

## Model

This is Recursive's **Flint**, the `RecursiveSI/flint-int4` Q4 checkpoint pinned by `packaging/flint-int4-mlx.json`, revision `3b93f9053b530488405ae9fca51d4900d6ce21f0`. It is the same full checkpoint used throughout the profiling campaign. All 12 files were verified by size and SHA-256. Local setup reuses those files in rec's standard model cache via hard links, avoiding another download or a duplicate 22.6 GB allocation.

## Run

The verified local build is installed as `~/.local/bin/rec`, pointing to the
managed copy at `~/.local/share/rec/releases/0.1.0-m4max-local/rec`.
That directory is already on PATH. The installed copy is independent of `.build/`.

From any directory, start the API server with a 32K total input/output budget:

```sh
rec serve --context 32768
```

While it is running, open another terminal to connect the preferred harness:

```sh
rec launch pi
```

The first harness launch may install the pinned pi client. Use `rec stop` to stop the managed server. The executable uses rec's standard data/configuration directory. There was no previous `rec` on PATH when this local version was installed. The manifest retains the upstream 262K maximum; 32K is a suggested initial setting matching the scope of this hardware campaign, not a new hard maximum.

## Rebuild

Use a new runtime output directory on each rebuild:

```sh
uv python install 3.12.12
"$(uv python dir)/cpython-3.12.12-macos-aarch64-none/bin/python3.12" \
  packaging/build-mlx-runtime.py \
  --python-root "$(uv python dir)/cpython-3.12.12-macos-aarch64-none" \
  --output .build/bundle-mlx-m4-rebuild
python3 packaging/package.py \
  --runtime-dir .build/bundle-mlx-m4-rebuild \
  --manifest packaging/flint-int4-mlx.json \
  --version 0.1.0-m4max-local --output .build/rec-m4-max
```

The initial local build reuses `.build/bundle-mlx`, generated by `make test`. Packaging embeds the modified Python engine and its dependencies, generates file/runtime hashes, and builds the Go CLI. A plain `go build` alone does not embed this runtime.

## Validation

`make test` passed: 62 engine tests without profile injection, Go race tests and vet, client/installer/package checks, packaged smoke inference, and protocol checks including pi/OpenCode tool round trips, streaming, cancellation and shutdown. The build log is `.build/m4-local-make-test.log`.

The actual `.build/rec-m4-max` executable (`rec 0.1.0-m4max-local`) then loaded the complete pinned Flint model through normal CLI/runtime selection and passed authenticated 512-token HTTP generation, an `add(a=2, b=3)` tool-call generation check, streaming completion and invalid-key rejection. No tool was executed. The test server shut down cleanly and is not left running. [Recorded verification](results/local-build-verification.json) contains the request counts and timings; these are smoke checks, not a new sustained performance benchmark.

The binary's `.meta` checksum was verified, and its embedded `device.py` hash matches the changed source. The standalone runtime reports the expected M4 Max 64/64/64 profile. The original binary and adjacent manifest/checksum remain under `.build/`; installation verified the copied executable's checksum and used the repository installer's managed-release directory and symlink layout.
